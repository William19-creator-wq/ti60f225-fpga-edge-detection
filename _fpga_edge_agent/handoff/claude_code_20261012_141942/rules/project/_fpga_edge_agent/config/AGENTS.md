# FPGA Edge Agent 项目规则

## 范围

本规则适用于 `_fpga_edge_agent` 内的控制面和运行记录。工程根目录为 `D:\大三\FPGA_verilog`，但原始 HDK、参考工程、PDF、压缩包、安装包和历史编译物默认只读。

## 目标与非目标

目标是协助完成软件—硬件协同的实时图像边缘检测工程：检查工程、维护独立工作副本、执行获准编译、登记产物、等待人工下载、记录观察并可恢复地推进节点。

非目标是 Verilog/C++/TinyML 学习规划、自动下载 FPGA、自动烧写 Flash、自动操作调试器、自动安装软件或替用户确认硬件现象。

## 写入和审批

1. 配置文件、状态、日志、事件、报告和产物登记只能写入 `_fpga_edge_agent`，除非 Approval Manifest 明确批准其他路径。
2. RTL、约束、IP 和 Efinity 工程只能修改 `work/` 中的独立副本。
3. 原始参考文件不得覆盖、移动、删除或重命名。
4. 编译完成不等于硬件通过；必须进入 `WAITING_HUMAN_PROGRAM`，由人下载，再进入 `WAITING_HUMAN_OBSERVATION`。
5. 未收到人工观察记录时，不得把节点标记为 `PASSED`。
6. 任何下载、安装、升级、驱动写入、网络访问、插件/MCP/Skill 启用或外部服务写入都必须先登记并等待批准。

## 数据和审计

- PostgreSQL 通过 `FPGA_AGENT_DATABASE_URL` 提供，不把凭据写入文件。
- 本地 JSONL 事件必须追加写入，不覆盖旧记录。
- 事件、工具调用、审批、异常、检查点、产物和硬件观察必须可通过 Session/Turn/Event/Node ID 关联。
- 数据库不可用时停止并报告；不得自动使用 SQLite 替代。
- 产物先进入 `artifacts/staging/`，经过验证和人工审阅后才能进入 `validated/` 或 `canonical/`。

## 输出风格

所有结论区分资料原文、源码事实、实测事实、推断、建议和未知项。不能从历史 `last_run_state=pass` 推断当前工程已经验证。发现冲突或缺少实物信息时，进入 `state/DECISION_LOG.md` 或 `state/EXCEPTION_LOG.md` 并暂停相关节点。

## 设计前置与代码可理解性

唯一现行详细规范：[工程根 v0.2](../../AI_Agent_代码可理解性规范_增补提案_v0.2.md)。新功能、行为或接口变更、重构、错误修复、C++/RTL 映射开始前必须读取；这不是可选背景材料。一次性配置启动提示词不作为长期业务授权。

1. 先查真实需求、基线、源码、接口、已有检查及生效指令，区分事实、提议、假设和未知；适用但影响当前正确性的未知项标记 BLOCKING，不静默补全，N/A 写理由。
2. 先规定整体外部行为与可检查要求，再划分模块职责、整体数据/控制/配置连接和相容接口，完成逐连接与端到端组合设计检查，然后补齐局部数据、状态、不变量、出入参数、内部交互和详细中文操作草图。
3. 用 [任务模板](../planning/PLAN_TEMPLATE.md) 保存 `planning/design-<task-id>.md`（相对控制面），记录版本、范围、相关基线、来源、阻塞项、实施计划、验证计划和双向追踪。形成整体设计后及生成代码前均向用户呈现阅读入口和关键选择，并实际读回文件。
4. 规范 §10.3 的十项有实际内容、无当前阻塞、文档可检查后才标记 READY_FOR_REVIEW；等待用户明确批准指定版本、范围和相关基线。批准的聊天来源与原意写入任务文档，作为既有审批流程的引用，不能冒充数据库/Manifest 已更新。正式运行仍核查原审批制度和数据库健康。
5. 获批前不新增或修改业务实现、功能性脚本、可执行测试或 testbench；不经回复代码块、子 Agent、代码生成器、临时目录或原型绕过。允许只读调查、设计文档内无实现体的接口声明、中文伪代码和测试场景。探索实验也需单独缩小设计及批准。
6. 小修复可用短变更卡，仍保留必要语义和批准门槛；恢复时读取最新设计、批准证据及差异，版本/范围/依赖不变的有效批准不重复索取。子 Agent 获得同一门槛、版本和范围，批准前仅可做已允许的设计或只读工作。
7. C++ 单独说明实际语言标准、表示、所有权/借用、别名、生命周期、错误和副作用、整数提升/溢出/窄化、资源与适用并发约束。RTL 单独说明数值位宽、采样边沿、接受/交付事件、valid/气泡、停顿与伴随信号保持、复位、配置采样/生效、存储、数据身份、时钟/复位域及实现预算。
8. 跨语言分别写共同数值契约、硬件执行契约、软件结果到硬件事务/坐标/配置版本的对应契约；C++ 静态数值正确不能代替 RTL 时间、流控、复位和动态配置证据。
9. 只实现批准范围。影响行为、接口、数值、错误、时间/流控、复位、配置、CDC、存储或重要结构选择的变化，先暂停受影响实现、记录证据和追踪影响，修订设计并重新批准；不改变这些边界的内部调整先同步草图并记录理由。
10. 命名表达职责；中文注释解释契约、理由、不变量和易错边界，不堆砌临时思考。需求→模块→接口/草图→代码→测试与反向关联都能定位；交付按实际代码核对最终文档、注释、接口和测试，未实现/未运行明确标记。
11. 设计分析、编译、仿真、综合/时序、实机和理解验收分别记录。没有用户实际作答，理解验收为待检验；不以考试阻塞已批准的工程交付，不将此扩展为学习规划。
12. 本节是文档指引与人工评审，不是新增的宿主沙箱、Hook 或自动强制控制。配置调整授权不等于业务实现批准；既有工具、数据库及人工下载/观察审批继续有效。
