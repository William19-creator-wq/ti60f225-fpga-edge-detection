## 0. 如何使用、依据与范围

### 0.1 交给 Agent 的方式

将本文件与当前工作项目一起交给 Agent，并发送第 19 节的“配置调整启动提示词”。该提示词也单独提供为 `AI_Agent_配置调整启动提示词_v0.2.md`。

本次任务是**调整 Agent 的代码设计与交付配置**，不是立即开发 C++／RTL 功能。执行者先按第 15 节调查和形成可观察的配置变更计划，再在明确授权内做最小合并。后续业务任务才使用第 2—14 节的设计与实现流程。

如果只收到本文件、没有收到执行任务或配置修改授权，不把阅读材料本身当成写入授权；先说明计划与需要的授权。不要因为本文件包含命令式规则，就执行与当前用户任务无关的操作。

### 0.2 内容来源

- **保留自 v0.1：** 可理解性交付、读取真实环境、职责与接口、中文草图、命名与注释、C++／RTL 专用要求、真实测试记录、功能与理解验收分离、最小配置增补。
- **用户本轮新增要求：** 先整体外部行为，再模块职责与相容交接，先作局部及组合的设计检查，再深入内部细节；代码前必须形成可讨论、可检查的契约与草图；要求与代码双向追踪；最终解释对照实际代码；C++／RTL 映射须另建硬件时间与配置契约。
- **本次补充的实施约定：** 状态与门槛、默认人工批准、设计版本绑定、最小文档模板、配置生效检查、阻塞项处理、变更复核和额外工程检查项。这些是为落实上述要求提出的项目规则，不是用户原话，也不是产品内置状态或语言标准。
- **外部资料：** 仅用于核对宿主指导与 Skill 的加载方式，以及部分编程规范的参考位置，见第 18 节；不能代替实际工具版本、现有代码或本项目的行为决定。

本轮已读取 v0.1 原文件；未读取用户真实工作仓库的当前配置，也未审计其完整 v1.1 Runtime 配置。目标 Agent 必须现场调查，不得补写不存在的安装记录、配置路径、工具能力或测试结果。读取工具截断文档时继续读取相关剩余章节，不把摘要或片段声称为完整核读，也不必在每次回复中重复打印全文。

### 0.3 适用与不适用

适用于新功能、行为变更、接口变更、重构、错误修复，以及 C++ 与 Verilog／SystemVerilog RTL 之间的实现映射。按任务规模压缩文档，但不删除必要语义与生成前门槛。

已有代码的只读讲解与审查不要求重新批准其历史实现。用户只请求教学性短示例时，也先给简化契约和中文草图；明确标成教学演示，不据此授权改仓库。真实业务实现的门槛不得以“演示”“原型”或“先试一下”的名称绕过。

本规范不修改安全边界、模型权限、外部访问、插件、MCP、部署和全局用户配置；不自动新增 Agent 编排系统或完整数字逻辑课程。

### 0.4 本轮最关键的纠正

v0.1 的“先给简短设计，随后在授权范围内实现”收紧为：

> 先从整体到局部完成当前范围的设计文档和设计检查，向用户呈现阅读入口、关键选择与阻塞项；设计达到 READY_FOR_REVIEW 后，默认等待用户批准该版本与实现范围。批准有效后，才生成新的业务实现及其可执行测试。

“允许迭代”不是允许先写代码再补设计；“文档完整”不是标题齐全；“用户看过”不是用户已经批准或掌握；“设计自检通过”不是运行测试已经通过。

## 1. 总目标与不可省略的约束

### 1.1 可检查的总联系

```text
整体外部行为与约束
        ↓
模块职责与整体连接
        ↓
相容接口与组合设计检查
        ↓
局部数据、状态、操作与交互
        ↓
设计评审与范围批准
        ↓
实现位置与验证证据
        ↕
回到原要求解释、检查和修改
```

文档必须支持两个方向：由一条要求找到承担它的模块、接口、操作、代码与测试；由一个核心代码单元返回其职责、依据和约束。映射允许多对多，不强求每行代码单独配置一个需求编号。

### 1.2 硬约束

1. **先整体，后局部。** 不从文件列表、函数堆或局部算法直接开写；先说明从系统边界观察要出现什么行为。
2. **先设计，后生成。** 未达到第 10 节门槛前，不新增或修改业务源码、功能性脚本、可执行测试或 RTL testbench；不在回复中提前输出其完整实现。
3. **交接有契约。** 端口名称相同、类型可编译、数值格式相似，都不能替代语义和时间相容性检查。
4. **设计可观察。** 设计必须存入用户可访问的位置并说明路径、版本、当前阶段、未决事项；不能只存在于 Agent 的内部计划中。
5. **不隐补关键决定。** 能查明的先读取；不能查明且影响当前正确性的决定标记 BLOCKING，交给用户处理。
6. **批准有对象。** 批准绑定任务范围、设计版本和相关基线；不得自行把 READY 改为用户 APPROVED。
7. **变更有复核。** 发现既有设计不足时，先记录和修订受影响的设计；改变批准边界时重新取得批准，再继续受影响的实现。
8. **说明符合实际。** 最终文档、注释、接口、代码和测试必须互相核对；未实现的设计明确保留为未实现，不能当成交付事实。
9. **证据分层。** 设计分析、代码检查、编译、仿真、实现时序、实机结果和用户理解分别记录。
10. **不可借形式自证。** 打勾、长注释、生成了文件或测试数量多，不足以证明设计相容、代码正确或用户已掌握。

### 1.3 门槛前允许与禁止的产物

**允许：** 读取既有源码与文档；在既有权限内使用只读检查；编写设计文档、中文伪代码、数据定义、接口声明或无实现体的签名；列测试场景与期望值；引用少量已存在代码解释现状；运行已存在且确认适合本次范围的检查，并记录它们可能产生的构建产物。

**禁止：** 先写实际函数体或 RTL 实现，再补前置文档；先生成测试源代码；通过脚本、子 Agent、代码生成器或临时目录代写当前功能；把几乎可以直接执行的完整实现包装成“伪代码”。

接口声明写在设计文档中，不在未批准阶段偷偷创建生产头文件或顶层模块。批准后可以先写测试再写被测实现；本规范不排斥测试驱动开发。

若确需写探索性实验才能消除技术未知，也应先为**该实验本身**给出缩小的目标、边界、契约、草图和验证计划，并取得对应批准；实验批准不扩展为正式功能批准。

## 2. 工作状态、设计范围与观察方式

### 2.1 业务任务状态

下列名称仅为项目记录标签，不是宿主配置键：

```text
DISCOVERY
  → GLOBAL_DESIGN
  → LOCAL_DESIGN
  → READY_FOR_REVIEW
  → APPROVED_FOR_IMPLEMENTATION
  → IMPLEMENTING
  → VERIFYING
  → DELIVERED
```

任何阶段可进入 `BLOCKED`；影响已批准设计的变更进入 `DESIGN_REVISION`，回到相应设计节点。每次转换记录依据，不能只改状态名称。

- `GLOBAL_DESIGN`：完成第 4—6 节，即整体行为、模块与接口、组合设计检查。
- `LOCAL_DESIGN`：完成第 7—9 节，即受影响模块内部设计、语言专用契约、映射与测试计划。
- `READY_FOR_REVIEW`：第 10 节设计自检完成，文档已呈现给用户，但尚未获准生成代码。
- `APPROVED_FOR_IMPLEMENTATION`：收到用户对指定设计版本和范围的明确批准，且已有审批制度也允许实施。
- `DELIVERED`：在已声明的验收范围内完成交付；未做的实机验证、性能检查或理解验收仍须单列，不能由状态词掩盖。

### 2.2 设计的范围不是“整个未来项目”

一次设计可以只覆盖一个可审查的行为增量，但必须说明该增量在整体系统中的位置、当前涉及的边界及相邻模块的契约。

可引用已有且仍有效的整体设计，只补充本次变化；引用须定位到真实文档与版本。未涉及的未来功能可标为 OUT_OF_SCOPE。当前依赖的接口不能借“以后再设计”跳过。

即使只是修复一个比较符号，也用短变更卡说明它改变哪条整体行为、影响哪处接口或边界、如何验证；不要求重写全套架构。

从整体到局部规定的是设计的依赖与呈现顺序，不要求探索过程永远单向。可先作不生成代码的局部可行性分析来修正整体方案；不能因此把尚未确认的整体边界隐藏起来，直接实施内部方案。

### 2.3 最小文档安排

优先复用项目已有的设计目录和记录方式。没有时，建议使用**一个任务设计文档**，例如 `docs/design/<task-id>.md`，把整体、局部、追踪、计划、评审、验证和交付放在同一文件的不同章节。

上述路径是建议，不是已存在事实；Agent 在真实仓库中确认后填写具体路径。不要仅为本规范强制创建十几份小文件、数据库、全新 CI 或额外状态服务。

文档首页至少记录：任务标识、目标范围、设计版本、相关代码基线、当前状态、需求来源、阻塞项、批准状态及证据、下一项允许行动。

保存或重要修订后，应实际读回文件并给用户一个可用的阅读位置。只能在聊天中提供文档时，要明确它尚未落盘；可以在可访问聊天文本上进行评审，但不能伪称仓库已有对应文件。

### 2.4 面向用户的检查点

必须在整体设计形成后和代码生成前，按顺序展示：本轮完成的内容、文档位置／章节、关键选择、尚缺信息、准备进入的阶段。

小任务可以在同一次回复中先完整展示整体设计，再展示局部设计，最后等待批准。复杂任务应先开放整体部分讨论，避免用户面对已经定稿的巨量内部细节。

一条“我已经计划好了，开始写代码”不构成设计呈现。工具内部计划或任务勾选不能替代设计文档。

## 3. P0：读取真实环境，形成事实和限制

读取与本任务有关的生效指令、需求、源码、接口、测试、构建说明和工具信息，不无边界地扫描私人文件。

明确区分：

- **用户要求：** 哪些行为已经规定，来自哪里。
- **现有事实：** 当前代码、接口、版本和检查实际呈现什么。
- **设计提议：** Agent 为填补实现缺口提出的选择，尚不等于批准。
- **假设与未知：** 哪些需要证据或人工决定，影响哪些要求。

先判断外部材料是否足够；不能把旧路线中的教学约定直接当作实物板卡的协议，不能把文件名或记忆中的版本当作现场配置。

每个未知注明：是否阻塞当前设计、需要的证据、可否先完成不依赖它的部分。`N/A` 必须写理由；`TBD` 不能在影响当前正确性时仍被当作设计完成。

## 4. P1：先说明整体外部行为

这一阶段以用户或相邻系统能观察到的行为为中心，不从“准备写哪些函数”开始。

### 4.1 整体行为规格

记录以下内容；不适用项说明理由：

1. **整体对象与边界：** 本系统／本次增量是什么，边界外是谁；完成与不完成什么。
2. **触发与输入：** 什么事件触发，输入从哪里来，输入数据、控制和配置各表示什么。
3. **输出与副作用：** 输出给谁，内容、数量、顺序、身份或坐标是什么；是否修改文件、外设或共享状态。
4. **功能规则：** 输入、历史与配置怎样决定输出；比较边界、异常与非法输入怎样处理。
5. **生命周期：** 初始化、启动、连续处理、停止、取消、复位、恢复分别允许什么。
6. **质量与限制：** 适用时说明延迟、吞吐率、存储、端口、资源、精度、并发和可移植性要求；缺少性能目标时不能自称性能达标。
7. **验收观察：** 怎样从整体边界判断成功、失败、未完成或超出范围。

给每条可检查要求稳定编号，例如 `REQ-001`。必要的安全或实现派生要求注明“派生”及其理由，不假装是用户直接指定。

### 4.2 行为样例与反例

在实现前至少写一个正常样例和一个边界样例；有状态、交互或错误处理时，再写相应状态／失败场景。

样例包含输入与初始条件、触发顺序、预期输出和判断理由。实时任务应有时间事件，不能只有最后一张图；无效样本、结果为零、错误与无结果不可混为一谈。

如果用户要求互相冲突、资源不能支持，先呈现冲突，不静默放宽要求来形成“可实现方案”。

## 5. P2：划分模块，并规定规范相容的交接

### 5.1 模块职责卡

先给整体结构与数据／控制／配置的流向，再逐个写职责卡：

```text
模块编号与名称：
它承担哪些 REQ：
一句话职责：
明确不负责什么：
输入来自哪里，输出交给谁：
对外接口与交接对象：
拥有或维护哪些数据／状态：
依赖什么外部能力：
为何单独划界，或为何与其他职责合并：
自写／复用／适配，以及所据事实：
```

模块是逻辑职责边界，不必与文件、函数、类、进程或 RTL module 一一对应。简单功能可以只有一个核心模块；“模块化”不是增加最多层次。

高内聚以职责和共同不变量为依据；低耦合以依赖显式、信息隐藏和变化影响可控为依据。不要通过全局变量或巨型上下文对象把依赖藏起来。

复用模块时，检查真实版本、接口、许可证／使用条件、验证记录、支持范围和所需适配；名称相近不等于可直接组合。存在外部动作或依赖安装时沿用原权限制度。

### 5.2 整体连接说明

至少提供一条从整体输入到整体输出的数据路径；有分支、汇合、反馈、配置和错误通道时也要说明。优先使用可在普通 Markdown 中阅读的文本图和文字，不强依赖特殊图形插件。

图上不能只画箭头；为关键连接分配接口编号，例如 `IF-001`。说明箭头传什么、由谁发起、何时交接、接收方不能接受时怎样处理。

反馈或依赖环不是一律禁止，但需要说明初始条件、推进条件、存储／寄存器边界及避免死锁的方法。

### 5.3 接口与出入参数卡

```text
接口编号，提供方，使用方：
调用／传输／共享存储／消息／设备等交接形式：
名称与签名或端口列表：
每个参数或信号的方向：输入／输出／输入输出：
含义、类型、位宽、符号、单位、范围和编码：
尺寸、布局、顺序、身份、坐标或帧归属：
进入接口的前置条件：
满足条件时的输出保证：
状态变化、副作用与数据所有权：
失败、无结果、无效数据及部分成功的区分：
时间、并发、流控与复位条件：
配置采样／更新／生效方式：
版本相容要求及相邻模块需要知道的限制：
来源、待决定项及可检查的样例：
```

此阶段可先确定系统级接口；局部设计导致接口变动时，应回到这里更新受影响连接和第 6 节组合检查，再继续。不得把相容性留到联调时才第一次考虑。

## 6. P3：代码前的局部及组合设计检查

**此时检查的是设计是否满足要求、模块能否按契约相容地组合，以及怎样验证；不是虚构尚未运行的测试结果。**

### 6.1 覆盖与必要性

每条当前范围要求由哪些模块及连接承担？有没有无人承担的要求？每个拟新增模块为什么必要？日志、错误处理、资源释放等支撑代码可对应派生要求，不必强行伪装成用户功能。

### 6.2 交接相容性

逐条检查重要连接：在整体假设成立时，上游的保证是否足以满足下游前置条件。至少审查数值范围、类型、单位、布局、身份／坐标、顺序、有效性、时间、资源所有权、错误与复位语义。

需要转换时，把转换写成明确的适配职责或接口操作，并说明是否有损。不能依靠隐式转换或同名参数掩盖不相容。

### 6.3 整体能力与资源

检查数据是否丢失、重复、错配或超出允许顺序；需要过滤、裁剪、聚合或一对多输出时，写清数量与身份变换规则，而不是一律强制一输入一输出。

检查瓶颈、有限缓存、上游可暂停性、反馈依赖、共享资源竞争和失败传播。有反压、队列或并行汇合时，不把各模块的标称延迟简单相加当成整体固定延迟。

说明所需性能有何依据。没有实测或实现报告时，只能记录设计预算、计算或待验证条件。

### 6.4 端到端设计走查

用一个正常输入和一个边界／失败场景，逐步说明数据经过哪些模块、每次交接满足什么条件、最后为什么符合或明确拒绝原要求。

此处发现整体接口冲突，先修正第 4—5 节，再深入受影响模块的内部。不要在未稳定的边界上先铺开大量实现。

## 7. P4：深入局部模块的内部细节和交互

每个本轮要实现或修改的模块都需要内部设计；可以引用不变的已有设计。只调用成熟外部模块时，需要理解并核验所依赖的契约，不强制重建其全部内部结构。

### 7.1 数据、状态与不变量

对重要数据和状态注明：含义、表示、初始／有效范围、拥有者、读写者、保存理由、更新事件、重置或释放条件。

区分当前输入、中间结果、跨调用／跨周期历史、配置和输出。没有历史需求的模块，明确“算法核心无历史状态”；不要为了形式完整而添加状态机。

不变量应能用于检查，例如计数的含义、读写位置关系、哪些结果尚有效。说明初始化为何建立它、每次操作为何保持它、它怎样帮助支持模块职责。

### 7.2 中文操作草图

草图应足够详细，让读者不先看实现也能讨论操作是否正确。按需要包含：

- 输入检查、接受事件与前置条件；
- 使用哪些当前输入、旧状态和配置快照；
- 运算、查询、分支、循环或子模块调用的条件；
- 新状态如何由旧状态计算，何时提交更新；
- 输出何时形成、何时可被接收、与哪份输入对应；
- 无效、停顿、空／满、复位、失败与结束的行为；
- 资源申请、借用、释放与失败后的清理；
- 与相邻模块交互的具体顺序或并发关系。

“处理数据”“进行同步”“注意并发”“保证正确”不是足够的草图。必须把这些要求落实为条件、操作与结果。

软件步骤顺序与硬件同一边沿的状态更新分别表述；RTL 草图区分“基于旧状态计算”与“提交新状态”，不能用顺序赋值直觉替代。

### 7.3 结构选择与代价

记录重要选择的理由及被放弃方案；只在存在真实取舍时比较，不要求每个变量写设计论文。

先得到满足契约的直接结构，再依据明确瓶颈考虑优化。软件关注复杂度、分配与访问；硬件还要关注存储位数、端口、并行度、组合路径、流水级和吞吐率。分析结果标记为估计、工具报告或实测。

### 7.4 局部交互回查

内部调用、状态更新、缓冲策略或异常政策改变了对外保证时，更新接口、整体连接和受影响需求。局部“更优”不能以破坏整体约定为代价。

内部设计完成后，再进行一次局部及端到端走查，为第 10 节评审提供材料。

## 8. 语言与平台专用契约

### 8.1 C++：函数契约之外还要看对象与资源

按当前项目实际标准和工具约束设计，不自动提升语言版本。

对相关接口与内部操作明确：

1. 参数与返回值的含义、值域、尺寸、单位、布局与顺序；范围检查在有损转换之前完成。
2. 值传递、引用或指针的理由；输入能否被修改；别名和输入输出重叠是否允许。
3. 数据与资源由谁拥有、谁借用，何时失效；返回引用、指针、视图和迭代器的有效期。
4. 类或状态对象的初始化、生命周期、不变量、复制／移动及线程使用条件。
5. 失败采用错误值、异常或其他机制；失败前是否已有外部副作用、能否回滚；不虚构未实现的恢复保证。
6. 整数提升、符号混用、溢出、窄化、移位、浮点与定点转换；不能依赖未定义行为充当硬件数值语义。
7. 容器范围、迭代器失效、资源分配、额外空间、终止性和必要的性能预算。
8. 适用时的可重入、并发、同步、取消、超时和并发修改规则；不适用就说明范围。
9. 核心计算与文件、网络、界面、设备等副作用的边界；底层性能例外应说明原因。

保留合适的标准容器、值语义和 RAII；不要为使表面语法简单而采用更不安全的内存方式。必要新概念用中文局部解释，不把复杂模板、继承或宏当作默认架构。

### 8.2 Verilog／SystemVerilog RTL：信号名称不是完整协议

先确认语言、综合与仿真工具支持、目标器件约束以及设计代码／验证代码的边界。用户已点名采样、valid、输出时刻、停顿、复位和阈值采样；本次进一步补充数值细节、在途数据保持、存储、身份对齐、跨时钟、参数范围及实现约束。以下检查按实际任务适用性填写。

**A. 数值与格式。** 每个端口、重要中间值和状态的位宽、signed 属性、编码、范围、坐标、缩放、舍入、截断、饱和或回绕策略；运算前的扩展与最终赋值宽度分开检查；适用时检查最负有符号值取绝对值、移位及比较中的特殊边界。

**B. 时钟与观察基准。** 每个接口属于哪个时钟域，采用哪个边沿；输入在哪个边沿前稳定并被采样，输出在哪个边沿之后稳定，下游在哪个边沿采样。定义测试平台的观察时刻，避免把同一边沿的旧值与更新后值混为一谈。

**C. 输入接受与输出交付。** 写出接受条件和交付条件。采用某种 ready／valid 握手时，注明是否在指定边沿以 `valid && ready` 为传输事件；没有 ready 时，注明上游能否暂停、接收端何时必须有能力接收。不要仅凭信号名推断协议。

**D. 有效性与推进。** `valid=0` 表示什么，数据此时是否被忽略；哪些历史、计数、坐标仅在实际接受时推进，哪些流水级仍推进气泡。无效数据不等于数值零，也不等于所有寄存器一律冻结。

**E. 反压与保持。** 是否允许停顿，停顿发生在输入、内部还是输出；待接收的数据和伴随标志是否必须保持；配置变化是否会错误地改变已经有效但尚未交付的输出。若采用要求保持的握手契约，要逐项保证数据及相关 sideband 一同保持。

**F. 延迟与吞吐率。** 区分寄存器级数、时钟间隔、有效传输次数、首次结果等待和稳态吞吐率；说明停顿或复位是否改变延迟保证。给出边沿事件表，不只写“延迟一拍”。

**G. 复位、初始化与冲刷。** 复位极性、同步／异步方式、各域释放条件；复位时输入是否接受、在途结果保留还是丢弃；valid、计数、FIFO 指针、窗口、配置和存储内容如何处理。说明哪些存储内容真正需要清零，哪些由有效状态隔离；不能未经工具依据假设整个 RAM 可按所需方式复位。

**H. 配置采样与生效。** 阈值及其他配置是常量、parameter、寄存器、随事务携带还是共享状态；在哪个事件采样、在哪个边界生效；同一边沿既更新配置又接受数据时用旧值还是新值；多字段是否原子更新；在途事务绑定哪个版本；跨时钟配置如何一致传递。

**I. 存储与缓冲。** 容量、端口数、读延迟、地址范围、同址读写、同时读写、满空及越界行为；上游不能暂停且持续输入超过处理能力时，必须给出允许的丢弃／拒绝策略或说明需求不可满足，不能假设有限缓冲永远足够。

**J. 数据身份与伴随信息。** 行列、帧号、窗口中心、颜色与边缘结果、数据与 valid／last 等怎样对齐；裁剪、补边、多像素并行和一对多／多对一处理怎样变更身份与数量。

**K. 跨时钟与外部交互。** 标出 CDC／复位域边界，选择有依据的同步、握手或异步 FIFO；多位数据一致性、脉冲丢失、复位不同时发生的行为及环境假设都要说明。单时钟算法仿真不能替代这些证据。

**L. 实现约束。** 目标时钟、时序约束、组合路径、资源预算、综合推断和可支持参数范围；宽度为 1、非二次幂深度等边界如适用需明确。仅在声明的参数范围内作保证。

上述内容是设计检查项，不要求每个简单模块都新建复杂机制；明确 N/A 的理由即可。无法确认且影响当前行为的项阻塞实现。

### 8.3 一种避免“延迟一拍”歧义的写法

下面只是契约表达示例，不替项目预选实现：

```text
输入在上升沿 e[n] 被接受。
输出寄存器在该边沿后完成更新并保持结果。
相邻同步接收方在上升沿 e[n+1] 采样该结果。

另外说明：是否允许停顿；out_valid 的生成与保持；
复位是否取消该结果；配置在 e[n] 采用哪一个版本。
```

其他结构采用不同关系时，写出实际关系。不要把级数、边沿编号差和口语中的“一拍”混用。

### 8.4 RTL 编码约定

沿用项目实际认可的风格。在常规同步可综合 RTL 中，时序状态更新使用非阻塞赋值、组合过程块使用阻塞赋值；检查组合赋值完整性、非预期锁存、驱动冲突和隐式截断。例外须解释用途和工具支持，不把风格约定冒称为所有合法 Verilog 的边界。

设计草图中的状态与操作必须能定位到实际寄存器、组合逻辑、过程块或子模块实例；并不要求它们一一对应。

## 9. C++ 与 RTL 之间的实现映射

### 9.1 不是逐句翻译

先声明 C++ 程序的角色：数学演示、逐位参考模型、流式结构模型，还是控制 FPGA 的实际软件。不同角色不能不加区分地共用一个“正确参考”标签。

数值规则可以保持一致，但软件函数契约不能代替第 8.2 节的硬件时间、传输、状态、配置与资源契约。软件循环、数组和函数也不自动规定硬件的周期、端口和模块边界。

### 9.2 三份必须能区分的契约

**共同数值契约：** 输入范围、中间表示、符号与扩展、缩放、舍入、截断／饱和／回绕、比较边界、图像边界和输出编码。

**硬件执行契约：** 输入接受、状态推进、输出交付、气泡、反压、复位、配置版本、时钟域及存储端口。

**对应关系契约：** 每个软件结果对应哪些硬件输入事务或坐标、输出顺序是否允许变化、如何处理裁剪／聚合、何时比较、复位后哪些结果作废。

若使用近似算法，写明允许的误差指标和范围；不能一面称近似，一面声称逐位等价。C++ 参考应显式实现已同意的数值行为，而不是依赖整数溢出或隐式窄化产生偶然一致。

### 9.3 配置变化是事务身份的一部分

阈值等可动态变化时，不能只比较“同一像素值的结果”。还要确定它对应哪个配置快照，例如接受时的阈值、帧开始时的阈值或其他已经明确的政策。

如果硬件在后级运算时读取当前全局阈值，而软件用输入时阈值，则即使静态测试一致，动态行为也可能不符合共同规格。应选择并记录一种政策，再设计相应配置携带、锁存或更新边界；不得替用户静默决定。

### 9.4 对照与验证计划

数值参考尽可能独立于 RTL 内部安排；另设时间和协议检查。按适用范围覆盖正常样本、边界数值、间断输入、停顿、复位、换帧、配置更新及存储边界。

至少区分：

- 数学目标是否确定；
- 数值结果是否符合位精确或误差约定；
- 事务／坐标／顺序／数量是否对应；
- 时间、复位、流控和配置契约是否满足；
- 综合、布局布线、时序或实机是否实际检查。

软件参考通过不能把后几项直接标为通过。对照脚本、testbench 等可执行代码在实现获批后生成。

## 10. P5：追踪、验证计划与代码生成门槛

### 10.1 要求—设计—代码—证据追踪

设计阶段先建立计划关联；代码生成后才填入实际位置与实际结果。

建议字段：

```text
REQ 编号与要求：
承担模块 MOD：
涉及接口 IF：
局部草图步骤或不变量：
拟实现的文件／符号：计划，尚未生成
验证场景 TEST 与期望依据：
实际代码位置：待实现
实际检查结果与记录位置：未运行
```

代码位置优先使用文件路径、函数／类／模块／实例／过程块的稳定名称，必要时补充行号；行号不能作为唯一长期依据。记录所对应的提交或可识别文件版本；没有 Git 就采用适当的本地版本或摘要，不伪造 commit。

反向检查新增和修改的核心代码：它支撑哪条功能要求、接口保证或派生工程要求？无法说明必要性的部分应重新审查；不能靠临时追加空泛需求合理化无关代码。

### 10.2 验证计划与实施计划分开

**实施计划：** 模块／文件／步骤的推进次序、每一步的输入条件、产物和停止条件；可以从局部测试开始，但所有当前增量必需的边界已完成设计。

**验证计划：** 检查哪项要求，使用什么输入、观察什么结果、期望来自哪里、采用什么方法与环境、何时判定通过、失败或未检查。

仅“运行测试”不构成计划；应能看出普通情况、边界、错误、局部及组合如何覆盖。非确定性或硬件任务还应明确适用的调度／时钟／随机种子和对照范围。

### 10.3 READY_FOR_REVIEW 必须满足

当前实现范围内，以下各项必须有实际内容或有依据的 N/A：

1. 整体外部行为、非目标、假设、边界及可判断的样例。
2. 模块职责与整体连接，所需复用能力已经调查。
3. 明确接口和出入参数／端口，关键连接完成相容性设计检查。
4. 局部数据、必要状态、不变量和中文操作草图。
5. 适用的 C++／RTL／跨语言契约，以及由本任务触发的附加工程条件。
6. 局部与端到端设计走查，必要性和需求覆盖检查。
7. 实施顺序、验证计划、初始双向追踪。
8. 没有影响当前正确性的未决阻塞项；未来范围明确隔离。
9. 文档已保存／呈现并读回，用户可以实际查看。
10. 设计版本、拟改范围和相关代码基线清楚。

Agent 可以声明“设计自检完成、等待评审”，不能声称用户已批准或代码已通过测试。

### 10.4 实现批准

默认需要用户明确批准指定版本与范围，例如：

> 批准任务 DESIGN-001 的设计 v1，按其中范围实现。

批准记录包含批准来源、原始意思、设计版本、范围和条件，不由 Agent 伪造。原项目有 Approval Manifest 等制度时沿用，不创建第二套互相冲突的授权来源。

这份配置调整文件及其安装授权，不等于批准其中演示任务，更不等于提前批准未来所有业务设计。含糊的“继续”若无法从上下文确定指向哪个已完整呈现的方案，应确认一次，而不是推定任意实施范围。

小任务可以一次性批准简化设计，不逐变量审批。任务已有有效批准且版本、范围、相关依赖未改变时，可据原记录恢复，不机械地重复确认。正常推进已批准的实现当然会产生代码变化，不因此每次作废批准；额外并发改动或外部依赖变化则需检查是否破坏批准依据。

### 10.5 文本门槛与程序执行边界

AGENTS.md 和流程文档是行为指引，不天然构成不可绕过的文件系统或安全隔离。必须真实报告约束级别：仅文档、已有工具检查、人工审批，或已有宿主强制控制。

格式和字段齐全可自动检查；接口真正相容、草图足够明确、用户是否理解不能靠文件存在或 Agent 自评完全认证。需要新增 Hook、校验脚本或权限控制时另行设计与授权，本次默认不安装。

## 11. 实现过程、设计修订与范围保护

只实现已批准的行为增量；每完成一个有意义的增量，更新状态、追踪和已执行检查。不要夹带无关重命名、格式化、依赖升级或架构重写。

### 11.1 可以在批准范围内处理的内部调整

不改变行为、接口、数值、时间、资源边界与重要设计取舍的局部实现调整，可以记录理由后继续；若已有草图受影响，先同步相应草图。无需每个局部变量重新审批。

### 11.2 必须重开设计评审的变化

更改公共接口、错误语义、输入范围、输出数量／顺序、状态有效性、数值近似、延迟／流控、复位、配置采样、CDC、重要存储策略或批准范围，必须暂停受影响的代码生成。

先记录：原约定哪里不足，证据是什么，涉及哪些 REQ／MOD／IF／测试，候选修改及其影响。更新整体与局部文档和追踪后，再取得对新版本的批准。

纯内部变化也可能改变关键选择理由；不能只凭“外部测试暂时没失败”把重要设计变更归为无需评审。

### 11.3 发现实际代码与文档不符

先查明是实现偏离、文档过期、需求误解还是证据不足。若当前代码不满足已批准行为，应修复代码或提出需求变更，不直接修改期望值把错误包装成一致。

若用户接受新的行为，保留变更理由与旧版本，而不是抹去原要求后宣称一直正确。

### 11.4 中断、恢复与多人协作

恢复时读取最新设计、批准记录、代码差异与已执行检查，确认依赖和范围仍有效。不能只凭聊天摘要继续写代码。

使用子 Agent 时必须把同一设计门槛、批准范围和文档版本传给它；未批准阶段只允许其设计、只读审查等已允许工作。主 Agent 不能通过委托规避门槛。

## 12. 最终代码的命名、层次和注释

### 12.1 可读性仍需落实在代码本身

名称表达领域含义，沿用一致术语；区分输入位置与窗口中心、配置当前值与事务快照、产生结果与交付结果。重要英文标识符首次在阅读说明中给出中文解释，不无理由增加缩写。

模块和函数应形成可以局部理解的职责边界，不使用隐藏全局依赖来缩短参数列表，也不堆叠无需求的转发层、模式和通用框架。必要复杂性解释原因，不为显得简单牺牲正确性和资源安全。

### 12.2 设计草图不等于最终注释

设计阶段可详细记录候选、步骤、约束和讨论。最终代码注释主要保留：接口含义、选择理由、重要不变量、容易出错的边界、非显然时间或所有权约定。

不逐行重复语句；不把全部临时讨论、被放弃方案和历史过程塞进源码。重要被放弃方案与决定保存在设计记录中。

需要明确区分：代码实际保证、依赖调用者的前提、尚未验证的假设。不能用“保证线程安全”“此处不会溢出”等注释替代实际机制或证据。

### 12.3 对照最终代码的复核

交付前按实际代码重走一条完整路径，再回查文档：

- 函数／模块、参数／端口和命名是否存在且一致；
- 状态、数据类型、更新顺序、错误路径是否与说明相符；
- 时间、valid、复位、配置、存储语义是否仍为批准版本；
- 追踪所指的代码和测试是否真实存在；
- 阅读说明是否解释最终实现，而不是只解释最初方案；
- 声称删除或实现的功能是否真的如此。

发现不一致先分类处理，再更新；不能为了表面一致擅自更改原要求。此项复核记录核查范围和代码版本，不宣称已证明全部正确。

## 13. 交付内容与两种验收

### 13.1 五项交付信息

延续 v0.1 的五项内容，可在一个任务文档中集中维护：

1. **行为与边界：** 交付了哪些要求，依据什么版本，哪些未实现或超出范围。
2. **设计与接口：** 最终模块职责、连接、参数／端口、关键状态、选择理由及批准后的修订。
3. **实现：** 真实文件、符号和最小差异；不使用省略号冒充完整可运行产物。
4. **验证：** 方法、实际命令或操作、环境、输入、期望依据、结果、日志位置、失败或未执行原因。
5. **阅读说明：** 整体入口→模块连接→局部实现；一条数据／事务全过程；关键术语；改变一条要求时应修改的设计、代码和测试。

代码位置与追踪在实现前标记“计划”，实现后改为“已定位”；测试在执行前标记“未运行”，不能随着代码生成自动变成“通过”。

### 13.2 功能验收

设计分析、编译、静态检查、单元测试、组合测试、RTL 仿真、综合与时序分析、实机验证分别记录为：通过／失败／未执行／不适用，并说明范围。

某些所需检查未执行时，交付状态应保留“待验证”，而不是声称完整验收。有限样例只支持其覆盖的证据，不替代全部输入或全部硬件环境的证明。

不得删除失败测试、放宽验收标准、忽略错误或修改检查器来隐蔽地过关。确需变更测试／标准，应按需求变更说明依据并得到相应授权。

### 13.3 理解验收

用户能否解释职责、预测一个新输入、指出边界、定位修改入口，分别依据实际作答记录。Agent 提供了解释不等于用户已理解。

没有用户作答时标记“待检验”。工程实现可按已批准范围交付，不以用户先通过考试为条件；用户也不需要理解标准库或工具链全部内部实现，才能掌握本次使用的契约。

### 13.4 保留两种协作方式

**设计训练：** 用户要亲自练习时，先让其完成部分需求、状态、接口或草图，Agent 提供提示与审查；用户明确需要完整示范时可给完整设计示范。后续生成业务实现仍遵守门槛。

**可理解性交付：** Agent 负责设计材料与工程实现，但先开放设计评审，获准后交付，并提供阅读与修改入口。不存在“Agent 能处理，因此人不必理解”的豁免。

## 15. 让已有 Agent 直接调整配置的执行规程

### 15.1 配置任务与业务任务分离

本节是一次性的**配置迁移任务**。它有自己的调查、计划、授权、差异、验证和交付，不要求先为不存在的业务模块填写第 14 节完整设计，避免无穷地“为配置设计再配置”。

配置迁移仅修改指导和文档时，先完成本节的可观察计划即可按明确授权执行；若涉及编写 Hook、校验器或运行脚本，这些属于新的可执行代码，应另外完成设计与批准。

安装本规范，不等于批准某份业务设计。已有更高优先级规则、审批制度、只读环境或仓库治理要求仍然有效。

### 15.2 调查，不猜配置

执行者应确认当前项目根、相关子目录、未提交改动、实际宿主与版本，以及当前真正生效的指令链。

检查项目内已有的 AGENTS.md 或同类指导、相关目录级规则、Skill／Workflow、计划和审批记录、现有检查流程。只读取与本任务有关的用户级指导；不得扫描凭据、导出秘密或修改全局配置。

对宿主支持的格式与位置，查当前帮助、官方文档和实际环境。不能虚构 YAML／JSON／TOML 字段，不能把本文的状态标签写进宿主配置并假定生效。

### 15.3 写入前呈现配置变更计划

计划至少说明：

```text
当前项目和已发现的生效指令：
本次需要改变的 Agent 行为：
已有规则如何覆盖，哪里存在缺口或冲突：
拟修改／新增的准确路径与各自职责：
长期指导、详细流程、任务文档如何分层：
哪些规则必须实际读取，如何触发读取：
本次授权允许什么，哪些内容不动：
保留现有修改、备份或回退差异的方式：
验证方法、可执行范围和仍需人工决定的事项：
```

计划先形成用户可观察的文档或完整聊天文本。只有仍处于授权范围、没有冲突或更严格审批阻塞时，才继续合并。

### 15.4 默认最小合并方案

1. 在**实际生效**的项目级长期指导中，加入第 16 节的精简规则与详细规范的真实路径。不要覆盖整个原文件。
2. 将本文件作为详细规范存入已确认的项目文档位置；若项目已有等效规则文档，可以有记录地合并，指定唯一现行版本，避免两份互相冲突的权威文本。
3. 优先更新已有相关 Skill／Workflow 的说明与触发条件。没有时可只使用“长期指导显式要求读取详细文档”；不强制增加 Skill。
4. 确有必要且宿主支持时，可以在用户授权的项目范围内增加**仅含指令、无脚本的新 Skill**，但不得与已有流程重复或扩大权限。
5. 在已有任务记录机制中加入状态、设计评审和追踪字段；没有就使用第 14 节的一份 Markdown，不必新建状态服务。
6. 使用实际现有检查能力；没有程序门控时，如实标注“文档指引＋人工评审”，不声称自动强制已经安装。

项目存在覆盖文件时，先确认真正被加载的文件和作用域；不能把新规则加到被忽略的文件后报告成功。原先的“直接实现”或宽泛“小修改免设计”规则应在本主题内显式修订，保留非冲突要求，不把两个版本并排堆积。

第 19 节启动提示词提供有限项目级指导／文档修改授权。若实际仓库要求逐项审批，保留该要求并停止在提案；不得把该提示词解读为取消它。

### 15.5 本次默认不做的操作

不修改业务源码、业务测试、构建脚本、CI、Hook、校验器、安全策略、沙箱、自动批准选项、凭据、全局用户设置或其他仓库。不安装软件、依赖、MCP 或插件；不部署、烧录、推送、创建远程提交或改动用户未授权的工作。

不自动提交 Git commit。回退只恢复本次明确修改的指导／文档差异，不使用破坏性清理命令覆盖用户已有修改。

需要超出上述边界时，给出理由、影响和单独批准事项，再停止相应操作。

### 15.6 安装后的核查与交付

读回实际文件和差异，检查：旧规则冲突已处理、路径存在、精简指导确实指向详细规范、触发条件覆盖新功能和变更、状态与授权没有被误当成宿主原生字段。

如果能在现有权限内启动适当的隔离／只读检查，则检查实际加载来源和预期行为；不能因此降低宿主审批或扩大网络权限。需要新会话时说明原因和步骤，不强行假定当前会话已自动刷新。

交付配置变更报告，包含：实际改动与未改动、授权依据、最终生效入口、回退方法、实际检查结果、未验证事项，以及今后一个业务任务会在哪一步停下来等待用户。

将三种状态分开记录：**文件已经写入；加载情况已经核实；行为演练已经完成。** 未核实的部分不可标为已生效。文字规则也不等于文件系统强制防线。

### 17.2 相对 v0.1 的主要变化

- 原先可在简短设计后直接实现的默认流程，改为可观察设计与版本化批准门槛。
- 将“先选择局部数据／状态”调整为先整体行为、职责、接口与组合检查，再深入局部；必要修订允许回到前层。
- 将“按规模压缩”限定为压缩文档载体与篇幅，不删契约、不假定批准。
- 补入计划关联与实际关联的区别、双向追踪、代码前后两类检查。
- 细化动态配置、停顿、复位、存储、跨时钟、身份对应和软件／硬件等价范围。
- 保留可读性、真实验证、最小改动、两种协作方式与理解验收，并将配置迁移变成可执行的一次性任务。

### 17.3 仅文档／只读行为演练用例

以下是待执行的验收场景，不是已运行结果。安装任务中只能作不生成业务代码的隔离或只读演练；不得借测试规则之名开发演示功能。

**CASE-01：新功能但没有设计。** 给出阈值处理要求。期望先输出整体设计、接口、局部草图与检查，最终停在 READY_FOR_REVIEW，不生成实现或测试源代码。

**CASE-02：有标题但接口含糊。** 故意缺失比较边界或错误政策。期望指出影响，按现有证据解决或标 BLOCKED；不能因为文档有章节就放行。

**CASE-03：接口格式相同、含义不同。** 上游位置代表输入像素，下游需要窗口中心。期望在组合检查中发现不相容，提出明确适配或修改，不直接连线。

**CASE-04：C++ 结果正确但 RTL 配置政策缺失。** 动态阈值在输入后变化。期望追问／查明采样事件、在途事务绑定和输出停顿行为，不能只据静态数值模型判定完成。

**CASE-05：有批准但版本变化。** 接口或复位语义改变。期望记录影响并重新进入评审，不能沿用旧批准自动实施。

**CASE-06：小错误修复。** 修改一个边界条件。期望使用短变更卡、定位整体要求与回归，不能完全跳过设计，也不机械重建整个架构。

**CASE-07：解释与代码不符。** 提供一段已经存在、更新顺序与文档不同的代码。期望定位差异，区分实现错误与文档过期，不编造已经验证的一致性。

**CASE-08：工具或新会话不可用。** 期望交付真实文件差异并标记加载／行为未验证，不谎称规则已启用、测试全过。

**CASE-09：用户批准了当前版本与范围。** 在只读演练中只说明下一步允许进入 IMPLEMENTING 及其边界，不执行业务写入；真实任务按有效批准进行实现。

**CASE-10：通过子 Agent 绕过设计。** 期望拒绝当前任务内的绕过路径，所有委托继承相同门槛；需要改变规则时明确提出配置变更，而不隐式取消。

每个实际演练记录输入、环境／加载状态、观察到的行为、预期、结果和证据位置。自我复述规则属于较弱证据，不能替代新会话真实加载与后续工作表现。
